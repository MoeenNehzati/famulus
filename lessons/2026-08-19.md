# 2026-08-19

## Agent instruction files are snapshotted at session start, so mid-session edits measure nothing

**Context:** Adding a `## Milestone logging` section to `CLAUDE.md`, then spawning subagents in the same session to see whether they followed it.

**Observation:** The subagents received the pre-edit file. A probe agent reported the section that follows the new one (`## Status labels`) while the new section was absent, which places the snapshot before the edit rather than after. The harness itself noticed the file had changed on disk and still did not reload it into context.

**Impact:** Any experiment on instruction wording run in the session that edited the instruction measures the old text. The failure is silent and looks exactly like non-compliance: the agent does the work, ignores the rule, and reports nothing unusual. Two full compliance runs were interpreted as "agents ignore the rule" before the cause was found.

**Use/Avoid:** Before concluding that agents ignore an instruction, ask one throwaway agent to quote the instruction back. If it cannot, the delivery is the bug, not the behaviour. To iterate on wording within one session, inject the text through the task prompt — that tests phrasing but not delivery, so confirm delivery separately in a fresh session before trusting the result.

## Give agents a command, not a derivation, when the value can be obtained wrongly

**Context:** Agents needed a session identifier to name a log file. The first design told them to derive it from a path already present in their context.

**Observation:** Real logs show every such agent falling back to the literal `unknown`. None reported a problem; the instruction was followed in form and produced a useless value. Replacing the derivation with a helper script that reads the identifier from the environment removed the failure class entirely, because no agent composes the value any more.

**Impact:** A derived value fails quietly and uniformly — you get files, they look plausible, and the correlation they were supposed to provide is absent. It also shrank the instruction by roughly a third, since the format and path rules moved into the script.

**Best bet:** When an instruction asks an agent to compute or look up a value, prefer a command that computes it. Reserve prose for what the agent must decide, which is the part no script can do. As a side benefit, host-specific details live in the script instead of shared instruction files that may not be allowed to name a platform.

## Single-run comparisons of instruction wording are too weak to conclude much

**Context:** Four runs of the same class of task, varying only the wording of a logging instruction: full text; full text plus a four-line worked example; a minimal version under a third the length; and a later revision using positive phrasing.

**Observation:** One run per arm, each task about twenty seconds and five or six tool calls. The arm stating "never narrate commands" violated it (`read SKILL.md and _rtx runtime`), and so did the arm that never stated it — so the prohibition has one negative data point, not two. The only arm to produce a goal-shaped entry rather than a file list was the one carrying the worked example, which is weak evidence *for* examples, not against them. The stated cadence of one line per 3-6 tool calls was exceeded by every arm, but at five tool calls the target cannot really be exercised. The minimal version matched the full version on everything measured, which is the sturdiest of the four comparisons and still rests on one run each.

**Impact:** It is easy to read four tidy-looking runs as four findings. Two of the four conclusions drawn from them were overstated and one was backwards relative to the raw entries, which were the only evidence available.

**Use/Avoid:** Treat one run per arm as a pilot that tells you the harness works, not as a result. Vary one thing at a time — the arm that differed by an example also differed in outcome, so nothing else in that arm can be read cleanly. Pick tasks long enough to exercise whatever the instruction asks for; a cadence rule needs a task with room for the cadence. Before writing a wording conclusion down, re-read the raw log lines rather than the summary written from them.

## Instruction delivery is universal across harnesses; agent identity is not

**Context:** Making one instruction work for subagents on both hosts the repo supports.

**Observation:** The shared instruction file reaches every subagent on both hosts, with no cooperation from the spawning parent. Everything else differs. On one host a subagent is told it is a subagent; on the other it is not, and cannot see its own task name even when spawn options set one explicitly. Neither exposes a usable identifier in context. Both expose one in the environment, under different names. Two other delivery routes do not work at all: content injected by a `SessionStart` hook does not reach subagents, and `@file` imports do not expand in agent definition files.

**Impact:** Anything an agent must know about itself has to come from the environment. Anything it must be told can come from the shared instruction file. Conflating the two produces a design that works on one host and silently degrades on the other.

**Use/Avoid:** Verify each channel with a throwaway probe agent that only introspects and quotes; do not infer capability from strings in a binary or from documentation. Two claims about subagent identity that were compiled into the binary turned out not to hold in practice.

## A test can pass vacuously when the operation it asserts silently skips

**Context:** Adding installer coverage for two new symlinks in `skills/install-assistant-tools/_rtx/tests/test_dev_link.py`.

**Observation:** The shared fixture `make_repo_root` did not create the source directory, and `make_link` skips a missing source with a log line rather than an error. The suite passed identically with the feature present and absent.

**Impact:** Link and copy assertions are especially prone to this, because the helpers that make them are deliberately forgiving about missing sources — the same tolerance that makes an installer robust makes its tests hollow.

**Use/Avoid:** After adding a test for an installed artefact, delete the production line and confirm the test fails, then restore it and confirm the source is unchanged. Check that the fixture actually creates every source the code under test consumes.
