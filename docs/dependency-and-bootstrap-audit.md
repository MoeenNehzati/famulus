# Dependency and bootstrap audit

This is the release-readiness record for executable bootstraps, managed
runtime dependencies, and vendored executable assets. The dependency and
installer inventory was reviewed against commit `e74b8ad7` on 2026-08-17 and
delta-reviewed through commit `a7d2fb28` on 2026-08-22; the vendored-asset
provenance was audited at commit `3bc38179` on 2026-08-15. The delta review
covered `75d08d30`, which moved optional-dependency selection into the

records what the current installer does; it is not a lock file or a
software-composition analysis of a future release.

## Shipped installation path

The public plugin contains Python source and JavaScript assets. The local
installer builds the checked-out or installed first-party Officina package
into a wheel, records that wheel's SHA-256 digest and source revision, and
installs it into a managed Python environment.

The bootstrap path is:

| Component | Current control | Provenance and integrity |
| --- | --- | --- |
| `uv` | Exact version `0.11.29` in `install-info.toml` | Downloaded from the matching `astral-sh/uv` GitHub release; the installer verifies the release's same-origin SHA-256 file before execution |
| Managed Python | Exact CPython `3.11.15` | Created with pinned `uv` using `--managed-python`; the release artifact records implementation, version, build, compiler, platform, cache tag, and executable identity |
| Officina wheel | Built from the selected plugin or checkout | Installed with `--no-deps`; the release artifact records the source revision, wheel name, and wheel SHA-256 digest |
| Core build/runtime packages | Universal lock in `references/runtime/requirements-core.lock` | The committed lock was generated by `uv 0.11.29` for Python `3.11.15` with exact versions and SHA-256 hashes; installation uses `--require-hashes` |

The `uv` checksum protects against a corrupt or mismatched download. Because it
is fetched from the same release origin as the executable, it is not an
independent signature or attestation. That limitation is acceptable for the
first release only as a documented bootstrap policy; adding signing or an SBOM
is not a first-release requirement.

Claude Code and Codex are host prerequisites. The Famulus installer probes
selected host commands but does not download or version those CLIs.

## Declared non-package dependencies

The same manifest declares what Famulus expects to find on the host rather than
install. Nothing here is fetched, versioned, or hash-locked, which is exactly
why it belongs in a bootstrap audit: these are the declarations that reach
outside the managed runtime.

| Class | Declared | Release note |
| --- | --- | --- |
| Binary | `crontab`, `git`, `journalctl`, `launchctl`, `schtasks`, `systemctl` | Invoked as found on `PATH`. All but `git` are scheduler or log-reading tools used on the platform that provides them. |
| System service | `launchd`, `systemd-user`, `task-scheduler` | The native scheduler backends `recurring-tasks` renders units for; one per supported OS family. |

A missing binary or service is a platform capability gap, not an installation
failure. Core installation creates no recurring jobs, so nothing in this table
is exercised until a job is deliberately enabled.

The blueprints remain the authoritative direct-dependency declarations. The
existing blueprint sync generates `references/blueprint/runtime_dependencies.json`.
`scripts/generate-runtime-lock.py` pools every distinct core constraint, adds
platform markers, and compiles one universal lock. Incompatible duplicate
constraints fail resolution rather than using declaration order.

### Maintaining the runtime lock

Use the exact `uv` version named in `install-info.toml` to regenerate the lock:

```bash
scripts/generate-runtime-lock.py --uv /path/to/uv-0.11.29
```

The offline check requires no package resolution or network access:

```bash
scripts/generate-runtime-lock.py --check
```

The check proves that the generated input matches the blueprint manifest, the
lock headers name that input and the configured `uv` and Python versions, the
complete lock body matches its recorded SHA-256 digest, and every parsed record
contains a concrete `==` version and a SHA-256 artifact hash. Wildcard versions
such as `==26.*` are rejected.

Generation compiles and validates temporary files before replacing either
canonical file. An ordinary resolution or validation failure therefore leaves
the published input and lock unchanged. This is failure-safe publication, not
a cross-file crash transaction or cryptographic attestation. Authenticity
continues to come from the reviewed Git commit or release tag, while
`uv pip install --require-hashes` rejects artifacts that do not match the
recorded package hashes.
