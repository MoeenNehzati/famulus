# Fast Dispatcher Design

**Date:** 2026-08-04
**Status:** Implemented

## Objective

Make every dispatcher invocation a small, bounded routing and authorization
operation. First use and repeated use must follow the same fast path. Dispatcher
must never repair repository state, regenerate derived artifacts, inspect Git,
or derive certification currentness.

## Governing Principle

Dispatcher has two responsibilities:

1. resolve a requested exported interface to its process binding; and
2. decide whether the immediate caller is authorized at every crossed module
   boundary.

If the active routing data is missing, malformed, incompatible, or cannot
prove the request valid, dispatcher returns a structured error. It does not
repair, refresh, rebuild, synchronize, or fall back to repository-wide
discovery.

Certification is not an authorization condition. Missing, expired, stale,
malformed, unavailable, or unknown certification status is warning-only.

## Audit of the Current Design

The current route catalog does not satisfy the governing principle:

- a missing or stale route triggers repository inventory and graph rebuilding;
- an expired negative certification decision triggers repository-wide
  certification derivation;
- certification derivation performs Git inspection and node hashing even
  though its result is advisory; and
- route warm-up therefore scales with repository size rather than with the
  requested authorization path.

The five-minute negative-certification expiry is especially harmful. It
periodically moves validation work back into ordinary invocation and makes a
previously warm route cold again.

## Architecture

### 1. Activation-time dispatch snapshot

Blueprint synchronization owns repository discovery, schema validation,
identity uniqueness, graph construction, topology validation, and generation
of a complete dispatch snapshot. Installation activates an already generated
snapshot through the same mechanism.

Snapshot generation is atomic:

1. construct and validate a complete candidate outside the active location;
2. serialize deterministic data-only records;
3. verify that the serialized candidate reloads and preserves the canonical
   authorization graph; and
4. atomically replace the active snapshot only after every check succeeds.

A failed synchronization leaves the preceding active snapshot unchanged.

The active snapshot is the runtime projection of the authored blueprints.
Blueprint edits, additions, removals, or topology changes become active only
after successful synchronization. This is an activation boundary, not a
second authoring authority: the snapshot contains only deterministic facts
derived from the canonical blueprint graph.

### 2. Snapshot representation

The snapshot is versioned data-only JSON decoded through an explicit type
allowlist. Its allowed-route records contain:

- format version and authorization-semantics version;
- module identities, registration ancestry, and discovery status;
- exported interfaces and exact interface versions;
- normalized namespace routes and facade routes;
- normalized access policies;
- implementing behavioral-source identity;
- process-binding declarations required to compile invocation arguments; and
- safe diagnostic metadata required to explain a denial.

The snapshot contains no credentials, caller arguments, environment values,
certificate payloads, or target-process output.

Each activated generation is a directory containing `manifest.json` and
compressed, digest-bound interface-route records. The manifest maps a hash of
each exact caller/interface pair either to its allowed-route record or to an
inline canonical denial diagnostic. A small `current.json` pointer is
atomically replaced to activate one complete generation. Given a caller module
and target interface ID, dispatcher reads the pointer, manifest, and at most one
route record without parsing every route in the repository.

Generations live under the user's dispatcher data root, keyed by canonical
repository identity. They are generated by a separate snapshot-builder entry
point owned by blueprint synchronization and used directly by installation.
Dispatcher cannot invoke that builder. The builder also owns cleanup of old
generations; dispatcher never deletes or rewrites them.

### 3. Invocation path

Every host and nested invocation follows this path:

1. load the active snapshot manifest;
2. reject an unsupported, missing, or malformed snapshot;
3. load the requested interface route record directly;
4. resolve the immediate caller record;
5. evaluate every crossed namespace, facade, and terminal access policy;
6. verify the requested interface version and compile caller arguments against
   the stored process binding;
7. replay precomputed certification status when supplied, or emit a bounded
   status-unavailable warning; and
8. invoke the gateway through the runtime provider.

Dispatcher performs no repository traversal, blueprint discovery, schema
validation, graph construction, cache rebuilding, Git inspection, certificate
hashing, or network access.

There is no warm-up path. The first invocation and later invocations execute
the same bounded algorithm.

## Authorization Semantics

For immediate caller module `x` and a policy owned by module `y`, authorization
passes exactly when:

```text
x == y
or access.allow_all_modules
or ancestry(x) intersects resolved(access.allowed_callers)
```

The predicate is evaluated independently at every crossed namespace route,
facade export, and terminal export.

The following invariants remain mandatory:

- the caller is the immediate calling module, not an upstream caller;
- accepting a namespace or facade hop makes that owner the caller of the next
  hop;
- source identity and `uses_interfaces` do not grant runtime permission;
- naming a module admits its registered descendants, not its parent or
  siblings;
- an empty non-public allowlist is private to the owner;
- direct host calls are limited to eligible discoverable modules; and
- missing or ambiguous identities fail closed.

The snapshot stores the normalized facts needed to evaluate this predicate. It
does not store a caller-independent `allowed` Boolean.

## Certification Status

`skill-certifier` and `skill-drift` own certification and currentness work.
The snapshot builder accepts an already computed certification view; it does
not derive one. Installation and ordinary blueprint synchronization currently
publish status-unavailable decisions rather than inspecting Git or certificate
state.

Dispatcher reads the stored decision only to emit warnings. It must never
refresh it or derive status itself. Missing, incompatible, stale, expired,
malformed, unavailable, or unknown status produces a bounded warning and
cannot deny or delay an authorized invocation.

## Errors and Failure Behavior

Before gateway launch, dispatcher returns stable structured errors for:

- active snapshot missing;
- snapshot format or semantics version unsupported;
- snapshot malformed;
- caller or target absent;
- route ambiguous or incomplete;
- access denied at a named boundary;
- interface version mismatch;
- invalid caller arguments; or
- invalid process binding.

Errors explain the failed condition and identify the separate snapshot-builder
entry point that can repair it. Dispatcher never performs that repair. A
missing initial snapshot is bootstrapped by installation or that builder
directly, never by routing the builder through dispatcher.

After gateway launch, target stdout, stderr, and exit status pass through
unchanged.

## Performance Contract

Dispatcher resolution cost must be independent of total repository size. For
one invocation it reads a constant number of index records plus records on the
selected route.

The following operations are forbidden on the invocation path and enforced by
tests:

- Git commands;
- repository walks or blueprint inventory;
- repository-wide graph loading;
- schema validation;
- certification-state derivation;
- node hashing or manifest construction;
- automatic snapshot or route-catalog rebuild; and
- network access.

Performance verification must measure fresh processes, not only repeated calls
inside one Python process. Initial targets on the reference Linux host are:

- first fresh-process dry-run against a newly activated snapshot: p95 below
  100 milliseconds;
- subsequent fresh-process dry-runs: p95 below 100 milliseconds and median
  below 50 milliseconds; and
- no first-route penalty larger than ordinary measurement noise.

These targets cover dispatcher resolution and binding compilation, excluding
gateway execution and external service latency. Tests also assert operation
counts so a fast machine cannot hide repository-scale work.

## Verification

### Authorization equivalence

Generate snapshots from existing authorization fixtures and prove snapshot
resolution matches the canonical resolver for:

- self, public, exact-caller, and ancestor admission;
- descendant asymmetry and sibling denial;
- namespace and facade hops;
- nested immediate-caller replacement;
- private targets;
- direct host restrictions;
- missing and ambiguous identities; and
- interface-version and process-binding selection.

### Snapshot safety

Tests must prove deterministic generation, atomic activation, fail-closed
loading, malformed-record rejection, unsupported-version rejection, and that a
failed generation preserves the previous active snapshot.

### Runtime isolation

Replace repository inventory, graph loading, certification derivation, Git,
and network functions with test failures, then prove both first and repeated
dispatcher invocations still resolve from the active snapshot.

### Performance

Run fresh-process benchmarks for the first read of a newly activated snapshot
and for subsequent fresh processes reading the same snapshot. Both must satisfy
the performance and operation-count requirements. Assert that dispatcher
creates or modifies no route cache.

## Documentation Corrections

The adopted architecture must be corrected to state:

- uncertified or expired nodes remain runtime-callable when authorization
  succeeds, with warning-only certification diagnostics;
- blueprint discovery, graph validation, and certification derivation never
  occur during dispatcher invocation;
- dispatcher does not rebuild missing or stale runtime projections; and
- synchronization activates validated routing state atomically.

## Non-Goals

- repairing or synchronizing blueprints during dispatch;
- repository-wide validation during dispatch;
- certification or drift computation during dispatch;
- caller-chain propagation;
- source-level runtime authorization;
- process isolation against hostile same-user code; and
- optimizing gateway or external-service latency.
